Manifest

Permissions & scope

Manifest V3, no remote code, permissions scoped to azblue.com and the two Cloudflare Workers.

manifest.json

host_permissions is what lets the extension fetch azblue.com pages directly, bypassing the old CORS-proxy Worker entirely once installed.

// manifest.json (abridged)
{
  "manifest_version": 3,
  "permissions": ["storage", "sidePanel", "tabs", "scripting"],
  "host_permissions": [
    "https://www.azblue.com/*",
    "https://audit-state.bcbs-of-az.workers.dev/*",
    "https://schema-cors-proxy.bcbs-of-az.workers.dev/*"
  ],
  "background": { "service_worker": "background.js" },
  "side_panel": { "default_path": "sidepanel.html" },
  "content_scripts": [{
    "matches": ["https://www.azblue.com/*", "https://azblue.com/*"],
    "js": ["content.js"]
  }]
}
File Map

What each file is responsible for

FileRole
dashboard.html / .jsThe full tool. Scripts externalised and inline handlers replaced with delegated data-* attributes for MV3's CSP.
actions.jsDelegated event dispatcher — parses data-click="fn('a', this)" style attributes, no eval.
dashview.jsRuns inside the dashboard's iframe. Generated from dashboard.js so the CSS/render logic isn't duplicated by hand.
ext-glue.jsAdds the "Review on site" button to the dashboard's tab bar, only when running as an extension.
sidepanel.html / .jsReads the active tab's URL, maps it to an audit path, filters the published run's findings.
content.jsInjected into azblue.com. Resolves a finding's evidence to a DOM element and highlights it.
background.jsToolbar click handling, per-tab side panel enablement, message relay.
Message Types

How the pieces talk

Three message types cover everything — two through the background service worker, one directly to the content script.

// dashboard.html → background.js
chrome.runtime.sendMessage({ type: 'openSite', url: 'https://www.azblue.com/' });

// sidepanel.js → background.js
chrome.runtime.sendMessage({ type: 'openDashboard' });

// sidepanel.js → content.js (per finding, on expand)
chrome.tabs.sendMessage(tabId, {
  type: 'sa-highlight',
  spec: { category, detail, urls, items, text }
});
Shared State

What lives in the Worker's KV store

Both surfaces read the same keys from the audit-state Worker. The dashboard writes run and triage; the side panel writes triage only.

// KV keys, all namespaced mlaudit:<host>:<name>
mlaudit:www.azblue.com:run          // published dashboard data
mlaudit:www.azblue.com:triage       // { findingKey: { status, at } }
mlaudit:www.azblue.com:sitemap      // discovered page list
mlaudit:www.azblue.com:sitemap404   // 404 monitor history
mlaudit:www.azblue.com:excludeDirs  // English-only sections
Highlight Resolution

How content.js finds an element

Tried in order, first match wins. Some findings — metadata, title, canonical, noindex — have no visible element and correctly resolve to nothing.

SignalResolves to
Broken link URLThe exact <a href> matching that path
Empty/placeholder linkAll href="#" or blank-href anchors
Evidence text (items)Whole-word match in page text — short tokens require word boundaries
Footer-related<footer> or [role=contentinfo]
Heading / H1 categoryAll heading elements on the page
Image / link countAll images or links in scope
